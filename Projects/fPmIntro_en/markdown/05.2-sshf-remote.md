# sshf & Remote Servers — Same Workflow Everywhere

* **The pain without it**: memorize server IPs and logins, and re-adapt because local and remote work differently
* `sshf` connects to servers by **number or name**, and you use fPM the same way on the remote

::: cards
* **sshf**
  - Show the server list
* **sshf 3**
  - Connect by id
* **sshf gpu1**
  - Connect by name
:::

---

# Server Registry → Connect by Name

::: columns
:::: {.column width="40%"}
* The server list is registered by number, name, and host in `___pm`'s `Servers.md` (same style as the project registry)
* Flow: `cdf 1` (→ ___pm) → check `Servers.md` → `sshf jm2` → remote connect succeeds
* After connecting, the prompt changes to `nowage@jm2` — you never type an IP or port

# Learn Once, Use Anywhere — graceful degrade

::: htmlart compare
* **Local macOS** / Rich support
  - iTerm2 split
  - Open Finder
  - Copy to clipboard
* **Remote Linux** / Natural fallback
  - Plain cd / ssh
  - Missing features degrade automatically
  - Same commands still work
:::

* On a remote server too, `cdf` navigation, hub, and work flow behave **exactly like local** — no relearning cost

> Before → After: from "a different way per server" to "just as you learned locally, on the remote too"

# Remote / LAN Access Setup

::: columns
:::: {.column width="40%"}
* Configure remote/mobile access in the **Advanced** tab of hub Settings
* Add a LAN IP (`192.168.0.17`) to **bind host** and other devices on the same network can reach the hub
* **advertise host** (`jm4.local`) is the host exposed in QR/links; **ssh remote alias** is the remote-connect alias
* This setup ties `/qr` mobile viewing and `sshf` remote access into one hub
