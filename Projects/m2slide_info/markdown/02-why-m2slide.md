## 기존 도구의 빈틈과 m2slide의 답

---

## PowerPoint의 문제

* 바이너리 포맷이라 **git diff·코드 리뷰가 안 됨** — 무엇이 바뀌었는지 보려면 슬라이드를 눈으로 다시 훑어야 함
* 텍스트·레이아웃이 한 슬라이드에 뒤엉켜 있어 **내용만 고치려 해도 디자인까지 건드리게 됨**
* 여러 명이 동시에 고치면 **병합(merge)이 사실상 불가능**

---

## 순수 Reveal.js / 손수 만든 HTML 슬라이드의 문제

* 텍스트 기반이라 diff는 되지만, **슬라이드 한 장 늘릴 때마다 HTML 태그를 직접 침**
* 차트·수식·3D 뷰어 같은 요소를 쓰려면 **라이브러리 연동을 매번 손으로 구성**
* 콘텐츠 작성자와 마크업 작성자가 다른 조직이면 **협업 병목**이 생김

---

## 비교로 보는 위치

| 항목 | PowerPoint | 순수 Reveal.js | m2slide |
| :--- | :--- | :--- | :--- |
| 작성 방식 | GUI 드래그 | HTML 직접 작성 | 마크다운 |
| 버전 관리 | 어려움(바이너리) | 가능(HTML) | 쉬움(텍스트 diff) |
| 테마 변경 | 슬라이드마다 수동 재배치 | CSS 직접 수정 | `_config.yml` 한 줄 |
| 차트·수식 등 | 이미지로 붙여넣기 | 라이브러리 직접 연동 | 펜스드 블록으로 바로 사용 |
| 재사용 | 복사·붙여넣기 | 파일 수작업 | 목차 파일의 링크 구조 |

---

## m2slide가 실제로 바꾸는 것

* **콘텐츠와 디자인 분리** — 작성자는 글쓰기에만 집중하고, 외관은 테마 설정이 담당
* **텍스트 기반 저작** — 슬라이드 변경 이력이 git log로 그대로 남고, PR 리뷰로 검토 가능
* **컴포넌트 내장** — 차트·수식·3D·인터랙티브 요소를 별도 세팅 없이 바로 씀

```mermaid
graph LR
  A[PPT: 바이너리·수작업] --> X((빈틈))
  B[Reveal.js: 마크업 부담] --> X
  X --> C[m2slide: 텍스트 저작 + 내장 컴포넌트]
```

## 왜 지금인가

* 요즘 발표 자료·문서는 **AI가 초안을 함께 쓰는 경우가 많음** — LLM은 마크다운을 가장 잘 다룸
* 마크다운으로 저작하면 **사람이 다듬는 부분과 AI가 생성하는 부분을 같은 포맷으로 주고받을 수 있음**
* m2slide는 이 흐름 위에서 "AI가 초안을 쓰고, 사람이 다듬고, 도구가 완성된 슬라이드로 빌드"하는 파이프라인까지 갖추고 있음
